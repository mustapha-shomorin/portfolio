Blog

Field notes for dependable data systems.

Practical ideas on pipeline design, data quality, and building data products people can trust.

Data quality

Make data quality part of the pipeline contract

A pipeline is not reliable just because it completed. The output also needs to meet expectations that downstream users can understand.

Start with checks at the boundaries: required fields and types when data arrives, uniqueness and referential integrity after transformation, then freshness and volume before publishing. These checks turn assumptions into visible, testable rules.

When a check fails, preserve the evidence and make the failure actionable. Quarantine suspect records or stop the affected output instead of silently dropping data. A clear signal helps the team decide whether to repair, replay, or accept a documented exception.

Orchestration

Design pipelines so retries are safe

Failures are normal in distributed systems. A timeout can happen after a write succeeded but before the caller received confirmation, so a retry may repeat work.

Make each run repeatable: use stable source identifiers, deterministic processing windows, and writes that replace or merge by a well-defined key. For event streams, deduplicate with event identifiers and retain enough state to recognise replays.

Advance checkpoints only after the corresponding output is durable. Then test recovery deliberately by replaying a completed interval and checking that counts and business totals remain consistent. This is more useful than assuming a task will only run once.

Analytics engineering

Model data around the decisions it supports

Clean tables are not automatically useful tables. A model should make it straightforward to answer a real question without each analyst rebuilding the same joins and metric definitions.

Begin with the grain: state what one row represents, then separate measurable events from the descriptive dimensions used to group them. Define important metrics once, and make keys, null handling, and time zones explicit.

Finally, treat the model as an interface. Document freshness and ownership, test the assumptions that matter, and change the contract deliberately when consumers depend on it. That keeps reporting consistent as the platform evolves.
